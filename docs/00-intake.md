程序支持用户自定义【--user-data-dir=】对应的 Chrome 用户数据目录（Data/Profile）路径，也支持在用户授权范围内创建和管理独立调试 Profile。程序必须检查路径是否符合所选 Chrome 版本的 CDP 安全要求，避免与正在使用的浏览器 Profile 冲突；未经授权不得覆盖、清理、迁移或修改用户原有浏览器数据。

可以自定义 remote-debugging-port 的端口，默认采用 9223

程序必须支持用户自由选择 Chrome 可执行文件，包括多个便携版 Chrome。程序需要识别实际使用的 Chrome 版本、用户数据目录和浏览器实例，根据实际兼容性与安全条件启动 CDP。
优先兼容便携版 Chrome 的独立 Profile，同时允许配置专用调试 Profile。在所选 Chrome 版本要求的情况下，自动使用非默认用户数据目录及必要启动参数，不得因强制省略 --user-data-dir 而导致连接失败。
程序不得未经用户授权修改、覆盖、迁移或删除原有浏览器 Profile，也不得为了建立调试连接而降低浏览器安全保护。
程序必须区分 Chrome 进程启动成功与 CDP 实际连接成功。启动后需要验证调试端口、实际连接端点、浏览器实例及目标页面是否正确，并处理端口占用、浏览器已运行、启动失败、连接中断和误连其他实例等情况；不得未经授权接管或终止不属于本程序管理的浏览器进程。

我建议设计成一个 多级自愈引擎（Multi-Level Self-Healing Engine）。

程序需要有 DOM 与 Selector 智能故障检测，这是工具最重要的检测引擎。
我建议同时实现静态分析和动态分析。 两者不能互相取代。

静态分析
工具读取 .user.js，通过 JavaScript AST 分析源码，尽可能识别和提取与网页 DOM 交互的代码。对于动态生成、运行时计算、间接调用或无法静态确认的代码，必须明确标记分析边界，并交由动态分析或后续验证处理，不得宣称已经全部识别。
检测结果应该包含：选择器内容、源码所在行号、所属函数、作用范围、是否存在备用选择器，以及是否属于动态生成的选择器。
对于动态拼接的 Selector、复杂封装函数与运行时计算代码，必须标记为「需要运行时确认」，而不是假装已经全部识别。

动态分析
真正打开目标网站检查运行情况。

## 补充功能方向与核心约束

本程序的核心目标，是尽可能自动识别、诊断并修复由于目标网站页面结构、DOM、Selector 或相关网页运行机制变化而失效的油猴脚本，减少用户逐个使用 AI 工具手动排查和修复脚本的时间与成本。

程序必须建立完整的脚本处理流程，包括脚本导入、元数据分析、目标网站识别、浏览器连接、故障检测、根因分析、修复方案生成、代码变更、自动化测试、结果验证、备份保存及失败回滚。

程序应支持在真实的目标浏览器和油猴脚本管理器环境下验证脚本行为，不能把普通网页 DOM 检测或单纯的 JavaScript 执行结果直接等同于油猴脚本功能测试通过。对于不同脚本管理器、GM API、运行沙箱、依赖和注入时机产生的兼容性差异，需要在开发前期研究并明确支持范围。

程序需要检查所选 Chrome Profile 是否具备已确认支持的油猴脚本管理器、待测试脚本、必要权限和相应运行条件。对于独立调试 Profile，应研究并设计安全可靠的脚本导入、测试环境初始化和状态检查流程。没有实际安装、加载或运行待测脚本时，不得宣称已经完成真实脚本功能测试；需要登录或授权时，不得擅自复制原有 Profile 的敏感资料，也不得绕过网站或浏览器的安全机制。

程序应自动识别油猴脚本的元数据、匹配网址、运行条件、依赖与 DOM 操作逻辑，并允许用户管理或补充目标网站、目标页面及需要验证的功能场景。对于需要登录、特定用户操作或其他前置状态才能执行的功能，必须明确其验证条件。

程序应能够处理现代网页中的动态 DOM、异步加载、单页应用路由变化及其他可能影响脚本执行的页面机制。对于无法充分获取或可靠判断的页面状态，必须保留不确定性，不得假装已经完成检测。

修复引擎应优先采用本地静态分析、动态分析与可验证的规则修复方法，仅在必要且符合用户配置时使用 AI 辅助。AI 应用于分析或生成修复候选方案，不得将 AI 输出直接视为正确结果。

所有自动修复必须尽可能保持脚本原有功能、业务逻辑、元数据、权限要求及正常行为。优先采用最小必要修改，避免无关重构、大范围重写或为了消除错误而删除原有功能。

程序必须具备修复验证机制。只有实际通过相应验收条件的修复，才能标记为已验证成功。对于缺少充分证据、无法确认原始意图或可能导致新问题的修复，必须保留原始文件，标记为待确认或无法安全修复。

程序应支持用户配置自动应用策略。满足安全与验证条件的修复可以自动保存；未满足条件的修复不得静默覆盖原始脚本。所有写入操作应具备备份、版本记录、变更对比与可靠回滚能力。

批量处理必须支持独立任务状态、错误隔离、失败重试、取消、进度记录、修复结果汇总，并防止某个脚本的故障影响其他正常脚本。

程序需要明确修复产物的保存、导出和使用方式，并研究与实际脚本管理器之间安全、可靠的脚本更新流程，不得假设修改本地 .user.js 文件就会自动更新浏览器内已安装的脚本。

程序应提供脚本健康监控、故障历史、修复历史及可追溯的诊断记录，能够区分已经验证恢复、仅检测通过、仍然失效和无法确认等不同状态。

程序需要兼容用户自行选择的 Chrome 程序及便携版 Chrome，并根据实际 Chrome 版本、Profile 配置和安全限制决定 CDP 的正确启动方式。不能因为硬性禁止必要的启动参数而导致浏览器连接失败，也不得未经授权修改原有浏览器数据。

AI 功能应支持自定义 Base URL、API Key 和模型名称，具备必要的连接验证、模型发现兼容性处理、失败恢复、调用限制、成本控制及敏感数据保护能力。用户应能够决定是否启用 AI、允许发送哪些数据，以及何时由本地修复转入 AI 辅助修复。

程序需要考虑导入脚本、目标网页及第三方 AI 返回内容均可能不可信的情况，避免通过自动修复、自动执行或自动应用代码造成权限滥用、敏感资料泄露及其他安全问题。

程序必须区分 DOM 变化引起的故障与其他类型的脚本问题。对于权限、网络、浏览器兼容性、第三方服务、网站访问限制或未知业务逻辑导致的问题，应依据证据分类诊断，不得强行当作 Selector 故障修改。

以上内容属于产品目标、功能方向及关键行为约束。具体的技术方案、软件架构、模块设计、实现优先级、正式规格、功能验收、测试策略与发布范围，应由配套的《通用 GitHub 项目开发前期准备完整执行指令》进行深入研究、验证、设计及审查，不得未经依据擅自改变原始产品目标。
